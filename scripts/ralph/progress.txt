## Codebase Patterns

(Ralph: append new patterns to the BOTTOM of this section as you discover them.)

- **PDF cm matrix is the most error-prone code in this repo.** Always verify with property tests via `parse_stamp_placement` (in `src-tauri/src/pdf.rs` mod tests). Pure-arithmetic unit tests aren't enough — they encode the same wrong derivation as the broken code (see `.claude/CLAUDE.md` "Why pure-arithmetic unit tests aren't enough"). Reference: commit 1622433 (image_cm fix) and 9f2b85b (test refactor).

- **Two coordinate systems**: PDF content stream is in *raw* page space (origin bottom-left, Y up, points). The viewer applies `/Rotate` to produce *display* space. The user picks positions in display space; we store as `(xPt, yPt, w, h)` in display units; cm matrix maps unit-square → raw space. See `.claude/CLAUDE.md` "Coordinate System" + "PDF Image Stamp `cm` Matrix Recipe".

- **q/Q wrapping rule**: when adding stamp content to an existing page Contents stream, wrap the existing Contents in `q ... Q` first; otherwise polluted CTM from the original PDF leaks into the stamp. Already implemented in `append_content_stream` (commit e633776). Regression covered by `stamp_image_survives_polluted_ctm_in_existing_contents`.

- **PDF Image XObject unit-square mapping (PDF 1.7 §8.9.5)**: an Image XObject is drawn into the unit square (0,0)–(1,1) with the *first* sample at unit (0,1) and the *last* sample at unit (1,0). PDF already accounts for top-down storage vs bottom-up user space — do NOT add a manual Y flip. Minimal "draw upright at (x,y) size (w,h)" cm = `[w, 0, 0, h, x, y]`. Anything with negative `d` is suspicious.

- **Tauri 2 IPC pattern**: prefer frontend-driven flows. Tauri lets Rust emit events, but receiving a synchronous response from the frontend is awkward. For multi-step user decisions (e.g. conflict resolution), have the frontend pre-fetch info via a separate command, decide entirely in React, then invoke the executing command with all decisions baked in.

- **Frontend layout**: Zustand stores in `src/stores/`, IPC wrappers in `src/services/`, components in `src/components/`. One component per file. kebab-case filenames. Strict TS, no `any`, no `console.log` in production code.

- **Per-PDF stamp config — master-index rule (US-P2 + US-FIX1)**: stamp-store has `defaultConfig` (applies to every loaded PDF) + `overrides: Record<pdfId, Partial<StampConfig>>` (per-PDF). UI handlers in `preview-pane`/`stamp-controls` call `applyEdit(currentPdfId, partial)` for position/size/rotation edits, NEVER `setDefault` directly. `applyEdit`'s default-vs-override decision is purely index-based: if `pdfId === usePdfStore.getState().files[0]?.path` (the "master" — the first PDF in the file list) the partial writes to `defaultConfig`, so every unoverridden PDF inherits it; otherwise it writes to `overrides[pdfId]`. There is no bootstrap flag — repeated edits on the master keep writing default (this was the FIX1 bug: the previous "first edit ever writes default; everything after writes override" rule sent the second master edit to `overrides[master]`, breaking the user's "PDF #1 is master" mental model). When the master is later removed, files[0] becomes the next PDF and edits on it write to default automatically. `applyEdit` is a no-op when `pdfId` is empty (no PDFs loaded yet). Image / text / color / font / lockAspect edits remain on `defaultConfig` via the existing shims (those are global stamp setup, not per-PDF). Reads go through `getEffectiveConfig(currentPdfId)`. Tests: `src/stores/stamp-store.test.ts` "applyEdit — master-index rule (US-FIX1)".

- **Per-PDF export pipeline (US-P3)**: `stamp_pdfs` IPC now accepts `{ jobs: StampJob[]; outputDir; skipIndices? }` instead of a single shared placement. `StampJob` lives in `src-tauri/src/pdf.rs` (Deserialize + `#[serde(rename_all = "camelCase")]`); the matching TS interface is in `pdf-bridge.ts`. The frontend Export handler iterates `files` and calls `getEffectiveConfig(f.path)` per file to assemble the array — never re-derives merge logic itself. Non-async core is `pdf::run_stamp_jobs(jobs, output_dir, skip_indices)`; the Tauri handler `commands::stamp_pdfs` is a thin async wrapper, so per-job dispatch + image-byte caching are covered by sync cargo tests (no tokio runtime needed). Image bytes are cached by `image_path` so the typical case (same image, distinct positions across N PDFs) reads disk once. Tests: `pdf::run_stamp_jobs_applies_per_pdf_configs` builds 3 PDFs with distinct (x, y, w, h, rotation_deg) and replays each cm chain via `parse_stamp_placement` + `rotate_around` corner geometry — same property pattern as `image_cm_user_rotation_property`, applied to the stamped output rather than the matrix function.

- All 49 vitest tests pass; `npx tsc --noEmit` clean; 32 cargo tests pass (no Rust changes).
- Files changed: `src/stores/stamp-store.ts`, `src/stores/stamp-store.test.ts`, `src/components/preview-pane.tsx`, `src/components/stamp-controls.tsx`, `scripts/ralph/prd.json`, `scripts/ralph/progress.txt`.
- **Learnings**:
  - **The bootstrap rule belongs in the *store*, not the components.** Earlier attempts at writing this in the UI handlers produced two flavors of the same conditional in two files (preview-pane and stamp-controls each deciding "default vs override"). Making `applyEdit` the single store action collapses that to one switch keyed on `hasBootstrappedDefault`. Components stay mechanical: capture currentPdfId, call applyEdit. Future per-PDF edit sites (US-P3 and beyond) can use the same action without re-deriving the bootstrap logic.
  - **The "subsequent edits on the SAME PDF go to override" rule is the surprising part.** Naive readings of "first edit goes to default" might assume the bootstrap PDF *keeps* writing to default until the user switches PDFs. We don't track per-PDF bootstrap state — there's a single global flag. So if the user picks a position on PDF 0 (bootstrap → default) and then drags it slightly on PDF 0 again, that second edit is a PDF-0 override. Visually consistent (PDF 0 still shows the new position), but the store state diverges: PDF 0 has an override, others fall through to default. Caught + locked in by the test "second applyEdit on the bootstrap PDF writes its override, not default".
  - **Selector returning a primitive sidesteps the fresh-object trap.** `useStampStore((s) => s.getEffectiveConfig(currentPdfId).xPt)` calls `getEffectiveConfig` on every state change (returns a fresh object each time), but the selector picks a primitive (`xPt`) so Zustand's default `Object.is` equality check sees no change unless `xPt` actually moved — no spurious re-renders. Returning the merged object directly would have required `useShallow` from `zustand/shallow` (extra import + extra dep on field count).
  - **Image-upload auto-snap stays on `setSize` (default), not `applyEdit`.** Image is global (`setImage` writes to default). If the snap-to-aspect size went through applyEdit, on the first upload it'd bootstrap → default (fine), but on any subsequent image change while editing PDF X, the size would land on PDF X's override while the image itself replaced default — leaving PDFs Y/Z with the new image at the *old* size (wrong aspect). Keeping image-upload auto-snap on default keeps image-and-size paired. The AC's "no setDefault calls from UI handlers" rule applies to explicit position/size/rotation edits; image-upload's auto-snap is a side-effect of the global image change, not a user-edit.
  - **CLAUDE.md edit was permission-rejected — fall back to progress.txt's "Codebase Patterns" section.** Auto memory pattern: when documenting cross-iteration rules and CLAUDE.md is locked, append to `## Codebase Patterns` in progress.txt. The Ralph wrapper reads progress.txt every iteration anyway, so it's the canonical source for project knowledge that survives context resets.

  - **Move logic out of `#[tauri::command]` async fns to keep tests sync.** Cargo tests can't easily await across the Tauri handler signature (and there's no runtime fixture in this repo).   - **The bug from the user's POV was almost certainly a hit-target issue.** A bare `<button>&times;</button>` with no padding renders ~10×16 px (just the glyph's bounding box).
