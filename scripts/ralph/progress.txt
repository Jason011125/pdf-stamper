## Codebase Patterns

(Ralph: append new patterns to the BOTTOM of this section as you discover them.)

- **PDF cm matrix is the most error-prone code in this repo.** Always verify with property tests via `parse_stamp_placement` (in `src-tauri/src/pdf.rs` mod tests). Pure-arithmetic unit tests aren't enough — they encode the same wrong derivation as the broken code (see `.claude/CLAUDE.md` "Why pure-arithmetic unit tests aren't enough"). Reference: commit 1622433 (image_cm fix) and 9f2b85b (test refactor).

- **Two coordinate systems**: PDF content stream is in *raw* page space (origin bottom-left, Y up, points). The viewer applies `/Rotate` to produce *display* space. The user picks positions in display space; we store as `(xPt, yPt, w, h)` in display units; cm matrix maps unit-square → raw space. See `.claude/CLAUDE.md` "Coordinate System" + "PDF Image Stamp `cm` Matrix Recipe".

- **q/Q wrapping rule**: when adding stamp content to an existing page Contents stream, wrap the existing Contents in `q ... Q` first; otherwise polluted CTM from the original PDF leaks into the stamp. Already implemented in `append_content_stream` (commit e633776). Regression covered by `stamp_image_survives_polluted_ctm_in_existing_contents`.

- **PDF Image XObject unit-square mapping (PDF 1.7 §8.9.5)**: an Image XObject is drawn into the unit square (0,0)–(1,1) with the *first* sample at unit (0,1) and the *last* sample at unit (1,0). PDF already accounts for top-down storage vs bottom-up user space — do NOT add a manual Y flip. Minimal "draw upright at (x,y) size (w,h)" cm = `[w, 0, 0, h, x, y]`. Anything with negative `d` is suspicious.

- **Tauri 2 IPC pattern**: prefer frontend-driven flows. Tauri lets Rust emit events, but receiving a synchronous response from the frontend is awkward. For multi-step user decisions (e.g. conflict resolution), have the frontend pre-fetch info via a separate command, decide entirely in React, then invoke the executing command with all decisions baked in.

- **Frontend layout**: Zustand stores in `src/stores/`, IPC wrappers in `src/services/`, components in `src/components/`. One component per file. kebab-case filenames. Strict TS, no `any`, no `console.log` in production code.

## 2026-04-30 — US-002c
- New `src/components/conflict-dialog.tsx`: pure-function reducer (`conflictReducer`) + `initialConflictState` + `isConflictComplete` + `ConflictDialog` React component (modal with Overwrite / Cancel / Overwrite all / Cancel all buttons).
  - State shape: `{ total, currentIndex, decisions: ConflictDecision[], applyAllMode: 'overwrite'|'skip'|null }`.
  - `overwrite-all` / `cancel-all` fill `decisions[currentIndex..total)` in one step and jump `currentIndex` to `total`, so subsequent conflicts auto-resolve without re-rendering the dialog.
  - On completion, an effect fires `onDone(decisions)`; parent maps `decisions[i] === 'skip'` → `conflicts[i].idx` for `skipIndices`.
- Wired into `stamp-controls.tsx`: Export now (1) selects output dir → (2) calls `checkOutputConflicts` → (3) if no conflicts, runs stamp directly; else opens the dialog and runs stamp after `onDone`.
- Tests: `src/components/conflict-dialog.test.tsx` (11 tests) — covers all four buttons individually, the headline mixed scenario from the AC ("overwrite then cancel-all on 5"), `skip` then `overwrite-all`, fully manual mixes, post-completion no-op, and zero-conflict early completion.
- Files changed: `src/components/conflict-dialog.tsx` (new), `src/components/conflict-dialog.test.tsx` (new), `src/components/stamp-controls.tsx`, `scripts/ralph/prd.json`, `scripts/ralph/progress.txt`.
- **Learnings**:
  - `useReducer(reducer, total, initialConflictState)` — the third arg is an *init function* that receives the second arg. Cleaner than building the initial state inline; the reducer stays a pure binary function (state, action) which is what makes it trivially testable.
  - `STAMP_SUFFIX = "-stamped"` is duplicated on both sides of the IPC boundary (`pdf::STAMP_SUFFIX` in Rust, a const in `stamp-controls.tsx`). Keeping them in sync is a manual concern; if it ever drifts to a third caller, consider exposing `STAMP_SUFFIX` from `pdf-bridge.ts` as the single TS source of truth.
  - For dialog completion-callbacks, fire from `useEffect([state])` rather than directly inside the dispatch handler. The reducer should remain pure and synchronous; side effects (calling `onDone`) belong in the effect, which observes the state transition that the reducer already produced.
  - Acceptance-criterion-driven test naming: each test title in `conflict-dialog.test.tsx` directly mirrors a phrase from the AC list. Easy to audit "did we cover all the AC?" by reading test names.

## 2026-04-30 — US-R1
- Extended `image_cm_for_rotation` (`src-tauri/src/pdf.rs`) with an 8th parameter `user_angle_deg: f32` (CCW rotation around stamp center). The body is now `M_total = T_rotate^-1 · T(dx + w/2, dy + h/2) · R(user_angle) · T(-w/2, -h/2) · S(w, h)`, built from a new tier of affine helpers (`affine_mul`, `affine_translate`, `affine_scale`, `affine_rotate_deg`, `t_rotate_inverse`) added to the top of `pdf.rs`.
- `stamp_image` call site updated to pass `0.0` for now. US-R2 will wire the real angle through StampConfig.
- Tests (3 new): `image_cm_user_rotation_property` covers all four page rotations × seven user angles ({0, 30, 90, 145, 180, 270, 359}); `image_cm_user_rotation_zero_matches_legacy_matrices` is a byte-identity guard vs the previous closed-form expressions for each rotation; `stamp_image_user_rotation_zero_landscape_unchanged` is a real-PDF round-trip on a landscape /Rotate=270 page to make sure the call-site change didn't regress.
- Files changed: `src-tauri/src/pdf.rs`, `scripts/ralph/prd.json`, `scripts/ralph/progress.txt`.
- **Learnings**:
  - Replace closed-form match arms with composed affine helpers when the math grows beyond ~3 cases. `image_cm_for_rotation` previously had 4 hardcoded `[a,b,c,d,e,f]` rows; with user-rotation that would have ballooned to 4 × the rotation-matrix expansion. Building it as `affine_mul(T_rotate_inv, affine_mul(T(cx,cy), affine_mul(R(θ), affine_mul(T(-w/2,-h/2), S(w,h)))))` reads as the algebraic derivation, so anyone reviewing it can verify each step against the comment without expanding the 4 closed-form variants.
  - Property test pattern that survives matrix refactors: rotate the *expected display corners* geometrically (`rotate_around` helper) and compare against `apply_t_rotate(apply_cm(corner))`. The test never touches the matrix expression, so it can't accidentally encode the same wrong derivation as a buggy implementation (the c6a9a80 / 9f2b85b lesson applied to user-rotation).
  - Two related but separate sign conventions live in the same file now: PDF's `/Rotate` is CW (raw → display), but user rotation is CCW (industry convention for "rotate this image"). The `affine_rotate_deg` doc comment + the `image_cm_for_rotation` doc comment both call out CCW explicitly; future code that mixes the two should preserve that distinction in names (`*_deg_ccw`?) if it gets confusing.
